## Q1. YouTube Data API: upload quota cost, default quota, audit, the private-lock rule, OAuth Testing tokens

### Takeaway
All three upload-cost figures (1,600, about 100, and 1) are real, each for a different period. Since 1 June 2026, `videos.insert` costs 1 unit in its own "Video Uploads" bucket, with a default of **100 uploads/day per Cloud project**, separate from the 10,000-unit pool. The cap that matters for planning is therefore 100 uploads/day/project, raised through the audit and quota-extension form. The "unverified project → forced private" rule **has been removed**. Google's official API description changed between 3 and 14 Oct 2026 (revision-history entry reported as 2 Nov 2026). The OAuth "Testing" 7-day refresh-token expiry is still current.

### Cited Findings
**Quota timeline**
- Revision history (Italian copy, snippet): the docs and quota calculator were updated to reflect a video upload cost falling "from approximately 1600 units to approximately 100 units". Other snippets and a secondary source date this entry **4 Dec 2025** — [Revision history (it) [P-snippet]](https://developers.google.com/youtube/v3/revision_history?hl=it); [AdaptlyPost [S]](https://adaptlypost.com/blog/youtube-api-quota-extension)
- Revision history, **1 Jun 2026** (snippet): the API "is moving to a granular quota system", starting with `videos.insert` and `search.list`, which "will be charged to their own respective quota buckets. API calls to all other methods will be charged to the existing quota bucket" — [Revision History [P-snippet]](https://developers.google.com/youtube/data/revision_history)
- videos.insert reference (snippet): "A call to this method has a quota cost of 1 unit in the Video Uploads quota bucket", quota impact "100 calls per day" — [Videos: insert [P-snippet]](https://developers.google.com/youtube/v3/docs/videos/insert)
- Quota Calculator (snippet): `search.list` and `videos.insert` "have their own quota buckets", each with a default daily limit of 100, at 1 per call. Some cached copies of the same page still show 1,600, which is stale — [Quota Calculator [P-snippet]](https://developers.google.com/youtube/data/determine_quota_cost)
- Overview page: the default allocation is 100 `search.list` calls, 100 `videos.insert` calls, and 10,000 units/day combined for all other endpoints — [Getting Started [P-snippet]](https://developers.google.com/youtube/data/getting-started)
- Revision history, 3 Jun 2026: the new `videos.batchGetStats` costs 1 unit in its own bucket with a 10,000/day default. The method is present in the fetched discovery document — [Revision History [P-snippet]](https://developers.google.com/youtube/data/revision_history); [Discovery doc [P-fetched]](https://www.googleapis.com/discovery/v1/apis/youtube/v3/rest)
- Postiz's YouTube provider maps the API error reason `defaultVideoInsertPerDayPerProject` to "YouTube's daily upload quota is exhausted for today". This shows the per-project daily upload-call limit exists in production error responses, and it is separate from `uploadLimitExceeded` (the channel's own daily upload limit) — [Postiz youtube.provider.ts [P-fetched]](https://raw.githubusercontent.com/gitroomhq/postiz-app/main/libraries/nestjs-libraries/src/integrations/social/youtube.provider.ts)
- Secondary sources agree on the timeline: about 1,600 → about 100 on 4 Dec 2025, then 1 unit in a separate bucket of 100/day from 1 Jun 2026 — [Blotato [S]](https://www.blotato.com/blog/youtube-api-pricing); [getphyllo [S]](https://www.getphyllo.com/post/is-the-youtube-api-free-in-2026-quota-limits-costs-when-to-pay); [upload-post [S]](https://www.upload-post.com/youtube-api/); dev.to post "YouTube now counts uploads in their own bucket: 100 a day, one unit each" (title seen in search only) [S]

**Audit and quota extension**
- To get more than the default, complete an audit by submitting the "YouTube API Services – Audit and Quota Extension Form". Projects audited within the last 12 months can file for an additional extension. The form says the general quota "can be used for all endpoints except search.list and videos.insert. If you need additional quota for search.list and videos.insert you must specify the quota required for each of these methods separately" — [Quota and Compliance Audits [P-snippet]](https://developers.google.com/youtube/data/guides/quota_and_compliance_audits); [Audit & Quota Extension Form [P-snippet]](https://support.google.com/youtube/contact/yt_api_form?hl=en)
- July 2021 revision entry: an API Compliance Audit is required to get more than the default quota — [Revision History [P-snippet]](https://developers.google.com/youtube/data/revision_history)

**Unverified project → private (rule removed)**
- Official YouTube Data API v3 discovery document (`revision: 20261102`), field `VideoStatus.privacyStatus`, verbatim: "In a `videos.insert` request, if you don't specify a value for this property, the uploaded video's privacy status defaults to `public`. Certain uploads might default to `private` based on creator account settings, as explained in the YouTube Help Center. **Videos uploaded from unverified API projects are not restricted to private viewing mode.**" — [YouTube discovery doc [P-fetched]](https://www.googleapis.com/discovery/v1/apis/youtube/v3/rest)
- Dating the change: Google's official generated client `@googleapis/youtube` **40.0.0 (published 2026-10-03)** has only "The video's privacy status." **40.0.1 (2026-10-14)** and 40.0.2 (2026-10-22) contain the new sentence. The same release moved doc links to `/youtube/data/reference/rest/v3/…` — [npm @googleapis/youtube [P-fetched]](https://registry.npmjs.org/@googleapis/youtube)
- Search snippets describe a revision-history entry dated **2 Nov 2026** saying that videos uploaded through `videos.insert` from unverified projects are no longer restricted to private viewing mode, reversing the 28 Jul 2020 rule. A third search did not surface that entry; its newest visible entry was 1 Sep 2026, in a Hebrew copy — [Revision History [P-snippet]](https://developers.google.com/youtube/data/revision_history); [Revision history (he) [P-snippet]](https://developers.google.com/youtube/v3/revision_history?authuser=4&hl=he)
- The old rule (for context): projects created after 28 Jul 2020 were locked to private until audited, and locked videos could not be appealed — [Stack Overflow archive [S]](https://kiwix.lema.org/stackoverflow.com_en_all_2023-11/questions/66277512/youtube-videos-privacy-locked-on-upload)

**OAuth Testing status**
- A Cloud project whose OAuth consent screen has an external user type and publishing status "Testing" "is issued a refresh token expiring in 7 days", unless the only scopes requested are a subset of name, email and profile. Testing apps are limited to 100 listed test users. The fix is to change the publishing status to "In production", and apps with sensitive or restricted scopes must complete verification. Expiry shows up as `invalid_grant` — [Google OAuth2 [P-snippet]](https://developers.google.com/identity/protocols/oauth2); [Manage App Audience [P-snippet]](https://support.google.com/cloud/answer/15549945?hl=en); [Google Ads API common errors [P-snippet]](https://developers.google.com/google-ads/api/docs/get-started/common-errors)
- `https://www.googleapis.com/auth/youtube.upload` is described as "Manage your YouTube videos". Verification for sensitive or restricted scopes requires a YouTube demo video covering all OAuth clients in the project — [OAuth 2.0 Scopes [P-snippet]](https://developers.google.com/identity/protocols/oauth2/scopes); [Manage App Data Access [P-snippet]](https://support.google.com/cloud/answer/15549135?hl=en)
- A Workspace admin can mark an app as Trusted, which lifts the 7-day limit for that organisation's users — [Google docs via search [P-snippet]](https://developers.google.com/identity/protocols/oauth2/production-readiness/overview)

**Files and Shorts**
- Discovery document: the `videos.insert` media upload `maxSize` is 274877906944 bytes (256 GB) and accepts `video/*` and `application/octet-stream`. `captions.insert` max is 100 MB. `thumbnails.set` `maxSize` is 52428800 (50 MB) in the discovery document. `VideoStatus` includes `containsSyntheticMedia` ("altered or synthetic media") — [Discovery doc [P-fetched]](https://www.googleapis.com/discovery/v1/apis/youtube/v3/rest)
- Shorts of up to 3 minutes, square or taller, can be uploaded from 15 Oct 2024. A Help page says square or vertical videos of up to 3 minutes uploaded on or after 8 Dec 2025 are categorised as Shorts — [YouTube Blog [P-snippet]](https://blog.youtube/news-and-events/tall-updates-coming-to-shorts/); [YouTube Help 15424877 [P-snippet]](https://support.google.com/youtube/answer/15424877?hl=en)

### Inferences
- **Capacity:** about **100 public uploads/day per Google Cloud project** by default, not 6. Thumbnails, metadata updates and status polling come out of the separate 10,000-unit pool, so they no longer compete with uploads. To go past 100/day, either pass the audit and request more `videos.insert` quota, or use several projects. Running several projects to evade quota likely breaches the developer policies; that policy text was not re-checked this pass.
- The earlier report's P0 item "detect the private lock" is still worth keeping as a cheap check: read back `status.privacyStatus` after upload. The reasons are now creator account settings (for example "made for kids" or defaults) and stale rollouts, not the unverified-project rule. The "default cost 1,600" config value should change to a **per-project daily upload-call budget (default 100)** plus a units budget for the 10k pool.
- The binding limit for an unattended agent is now OAuth: an app left in **Testing** dies after 7 days. Moving to In production with `youtube.upload` requires Google verification, likely sensitive-scope verification with a demo video.
- The channel-level `uploadLimitExceeded` limit exists separately from API quota. Its numeric value is not published.

### Gaps
- Exact verbatim text and date of the 4 Dec 2025 and 2 Nov 2026 revision-history entries could not be read directly (developers.google.com blocked). The Nov 2026 change is confirmed by the machine-readable discovery document; its date rests on snippets and npm publish dates.
- Whether `youtube.upload` is classed as "sensitive" or "restricted" was not confirmed from a primary text. My expectation is sensitive, unverified.
- Current per-call unit costs of `thumbnails.set` and `videos.update` in the 10k pool were not re-verified. The discovery document gives 50 MB for thumbnails, while the human docs historically said 2 MB; not resolved.
- The channel-level daily upload cap (`uploadLimitExceeded`) has no published number.

## Q2. TikTok Content Posting API: tokens, audit restrictions, caps, UX, modes, rate limits, specs

### Takeaway
The unaudited-client rules are confirmed by TikTok's own pages: posts are private (SELF_ONLY) and at most 5 users can post per 24 h. The audited cap of "typically around 15 posts/day per creator, shared across all apps" is also confirmed, as are the 6 requests/min per token rate limit and the specs (≤ 4 GB, ≤ 10 min, 360–4096 px, 23–60 fps). Token lifetimes **conflict** across TikTok's own pages: 2 h / 180 days on the OAuth v2 get/refresh pages versus 24 h / 365 days elsewhere. Design for the shorter values and for refresh-token rotation.

### Cited Findings
- Content Sharing Guidelines: each creator has a Direct Post limit per 24 h that "may vary among creators (typically around 15 posts per day/ creator account) and is shared across all API Clients using Direct Post". Each API client also has a 24-hour **active creator cap** based on the usage estimates in its audit application — [Content Sharing Guidelines [P-snippet]](https://developers.tiktok.com/docs/en/content-sharing-guidelines)
- Unaudited: "Unaudited clients can allow up to 5 users to post in a 24-hour window". Content is limited to private viewing, and accounts must be private at the time of posting. Direct Post reference: "All content uploaded via this endpoint will be restricted to private viewing mode. To lift this restriction, your API client must undergo an audit" — [Content Sharing Guidelines [P-snippet]](https://developers.tiktok.com/docs/en/content-sharing-guidelines); [Direct Post [P-snippet]](https://developers.tiktok.com/docs/en/content-posting-api-reference-direct-post)
- `creator_info/query` must be called when rendering the posting page. If the creator "can not make more posts at this moment", the client must stop and prompt the user to retry later. The response gives `privacy_level_options` and `max_video_post_duration_sec` — [Query Creator Info [P-snippet]](https://developers.tiktok.com/docs/en/content-posting-api-reference-query-creator-info)
- Required UX (guidelines): show the creator's nickname. The user must choose the privacy status manually with no default. Interaction settings (comments, duet, stitch) must not be on by default. Duration must be checked against `max_video_post_duration_sec` — [Content Sharing Guidelines [P-snippet]](https://developers.tiktok.com/docs/en/content-sharing-guidelines)
- Rate limit: 6 requests per minute per user access token (HTTP 429 `rate_limit_exceeded`). At most 5 pending shares in any 24-hour period (403 `spam_risk_too_many_pending_share`). Accepted content types: `video/mp4`, `video/quicktime`, `video/webm` — [Upload [P-snippet]](https://developers.tiktok.com/docs/en/content-posting-api-reference-upload-video); [Direct Post [P-snippet]](https://developers.tiktok.com/docs/en/content-posting-api-reference-direct-post)
- Specs (Media Transfer Guide): MP4 (recommended), WebM or MOV. H.264 recommended; H.265, VP8 and VP9 also supported. 23–60 FPS. 360–4096 px for both height and width. Maximum 4 GB. "The longest video a developer can send via the initialize Upload Video endpoint is 10 minutes", and users may trim it to their own limit. `PULL_FROM_URL` URLs must be on a verified domain and stay reachable; downloads time out 1 h after starting. Status errors include `duration_check_failed` and `frame_rate_check_failed` — [Media Transfer Guide [P-snippet]](https://developers.tiktok.com/doc/content-posting-api-media-transfer-guide)
- Tokens (conflict):
  - "Refresh a User Access Token" / "Get a User Access Token" (OAuth v2): access token valid **2 hours**, "The refresh token is valid for **180 days** after the initial issuance". A refresh returns a new refresh token; use the latest one — [Refresh a User Access Token [P-snippet]](https://developers.tiktok.com/docs/en/oauth-refresh-a-user-access-token); [Get a User Access Token [P-snippet]](https://developers.tiktok.com/doc/oauth-get-a-user-access-token)
  - Manage User Access Tokens, Silent Login, Legacy and Minis pages: **24 h / 365 days**, with rotation ("must use the newly-returned token") — [User Access Token Management [P-snippet]](https://developers.tiktok.com/docs/en/oauth-user-access-token-management); [Legacy guide [P-snippet]](https://developers.tiktok.com/doc/legacy-user-access-guide); [Minis OAuth [P-snippet]](https://developers.tiktok.com/doc/minis-oauth)
  - Client (app) access tokens are valid 2 h — [Client access token [P-snippet]](https://developers.tiktok.com/doc/client-access-token-management)
- Error codes seen in production code (Postiz): `spam_risk_too_many_posts` ("daily post limit reached"), `spam_risk_too_many_pending_share`, `spam_risk_user_banned_from_posting`, `spam_risk_text`, `reached_active_user_cap` ("TikTok daily user limit reached" for the app), `unaudited_client_can_only_post_to_private_accounts`, `privacy_level_option_mismatch`, `url_ownership_unverified`, `duration_check_failed` — [Postiz tiktok.provider.ts [P-fetched]](https://raw.githubusercontent.com/gitroomhq/postiz-app/main/libraries/nestjs-libraries/src/integrations/social/tiktok.provider.ts)
- Direct Post vs Upload (as documented in Postiz code): "`DIRECT_POST` publishes the post to the account. `UPLOAD` does NOT publish: it only sends the media to the user inbox of the TikTok app, where the user must manually complete and publish it within 24 hours or it is discarded." Also: "With UPLOAD, TikTok ignores every setting except the title". Postiz uses `/inbox/video/init/` for UPLOAD. Chunks must be 5–64 MB; files ≤ 64 MB go in one chunk — [Postiz tiktok.provider.ts [P-fetched]](https://raw.githubusercontent.com/gitroomhq/postiz-app/main/libraries/nestjs-libraries/src/integrations/social/tiktok.provider.ts)

### Inferences
- **Capacity per TikTok account:** about 15 Direct Posts/day (query `creator_info` and do not assume). Upload/inbox mode allows at most 5 pending items per 24 h and needs a human to finish each one, so it is not a batch path. **Per app:** the active-creator cap from the audit application limits how many accounts one audited app can run per day, so the audit application's usage estimate should match the planned number of accounts.
- **Before audit:** zero public posts, and only 5 posting users per day, all of whom must have private accounts.
- **Token design:** refresh proactively against `expires_in` from each response, not a constant. Persist the rotated `refresh_token` atomically. Treat `refresh_expires_in` (180 or 365 days) as the re-consent horizon.
- At 6 init requests/min per token, rate limits are not the bottleneck at 15 posts/day.

### Gaps
- Which token lifetime (2 h/180 d or 24 h/365 d) TikTok actually issues today for Content Posting scopes: the official pages conflict and none could be fetched. Verify with one live token response.
- Whether posts made before the audit stay private after the audit (claimed earlier): not re-confirmed this pass.
- Exact required commercial-content and music-usage-confirmation wording for the audit: not re-verified this pass.
- No minimum video duration was found in the snippets.

## Q3. Meta: Facebook Page Reels (`/video_reels`) and Instagram Reels

### Takeaway
Facebook Page Reels: `POST /{page-id}/video_reels` (start → rupload → finish) with a cap of **30 API-published reels per 24 h rolling window**. Specs are 9:16, 3–90 s, 24–60 fps and ≥540p. It needs `pages_manage_posts`, `pages_read_engagement` and `pages_show_list` on a Page token, **Advanced Access through App Review plus Business Verification** to serve Pages outside the app's roles, and a separate Tech Provider access verification. Instagram's limit is documented inconsistently by Meta itself (100 versus 50 per 24 h); 50 is the safer planning value, and `content_publishing_limit` gives the live number.

### Cited Findings
- Reels Publishing API: 30 API-published posts per 24-hour moving period, enforced on the `video_reels` endpoint. Frame rate 24–60 fps. Error text "Reels duration must be between 3 and 90 seconds" — [Reels Publishing API [P-snippet]](https://developers.secure.facebook.com/documentation/video-api/guides/reels-publishing). Rolling window, scheduled reels count toward it, 9:16 — [Ayrshare [S]](https://www.ayrshare.com/docs/apis/post/social-networks/facebook); [Apify [S]](https://apify.com/dami_studio/facebook-reels-uploader). Minimum 540p and "cannot read/update/delete via this edge" were confirmed in the previous pass — [Meta Reels guide [P, previous pass]](https://developers.facebook.com/documentation/video-api/guides/reels-publishing)
- Page `video_reels` reference (v26.0): POST `/{page_id}/video_reels`, supports `scheduled_publish_time`, and "no Graph object will be created" on the edge — [Page Video Reels reference [P-snippet]](https://developers.facebook.com/docs/graph-api/reference/page/video_reels)
- Permissions: publishing a video or Reel to a Page requires a Page access token with `pages_show_list`, `pages_read_engagement` and `pages_manage_posts` — [Publish with the Video API [P-snippet]](https://developers.facebook.com/documentation/video-api/guides/publishing)
- App Review and Business Verification are required for Advanced Access. Access Verification (Tech Provider) applies to `pages_manage_posts`; without it, calls fail with error 100 for users without an app role — [Permissions Reference [P-snippet]](https://developers.facebook.com/docs/permissions); [Business Verification [P-snippet]](https://developers.facebook.com/docs/development/release/business-verification/); [Access Verification [P-snippet]](https://developers.facebook.com/documentation/development/release/access-verification.md)
- Tokens: short-lived user tokens can be exchanged for long-lived ones (about 60 days). Page tokens are per Page, admin and app. System User tokens under Facebook Login for Business can be non-expiring — [Access Tokens [P-snippet]](https://developers.facebook.com/documentation/facebook-login/guides/access-tokens); [Facebook Login for Business [P-snippet]](https://developers.facebook.com/documentation/facebook-login/facebook-login-for-business)
- Stories differ: Page video stories are 3–90 s, and a reel published as a story cannot exceed 60 s — [Page Stories API [P-snippet]](https://developers.facebook.com/documentation/video-api/page-stories-api)
- Instagram: the Content Publishing guide says "100 API-published posts within a 24-hour moving period" (carousels count as one). The `media_publish` reference says 50, and `content_publishing_limit` shows `quota_total` 50 over `quota_duration` 86400. The 2021 launch figure was 25 — [Content Publishing [P-snippet]](https://developers.facebook.com/documentation/instagram-platform/content-publishing.md); [IG User Media Publish [P-snippet]](https://developers.facebook.com/documentation/instagram-platform/instagram-graph-api/reference/ig-user/media_publish); [Content Publishing Limit [P-snippet]](https://developers.facebook.com/documentation/instagram-platform/instagram-graph-api/reference/ig-user/content_publishing_limit.md)
- Postiz's Instagram error text cites limits of 300 MB, 1920 px width and 25 Mbps bitrate for video. It uses `media_type=REELS` — [Postiz instagram.provider.ts [P-fetched]](https://raw.githubusercontent.com/gitroomhq/postiz-app/main/libraries/nestjs-libraries/src/integrations/social/instagram.provider.ts)

### Inferences
- **Capacity:** 30 FB Page Reels/day per Page and 50 (possibly 100) IG posts/day per IG account. For our project, Facebook is not the bottleneck; TikTok (about 15) is.
- Our current `facebook_publisher.py` (`/{page_id}/videos`, v23.0) should move to `/video_reels`. Postiz also still uses `/videos` and only builds a `/reel/` URL, which suggests `/videos` uploads may surface as reels. That is not documented by Meta, so the documented `/video_reels` path with its explicit 30/24 h limit is the safer one.
- For an unattended server, a Business-owned **System User** token avoids the 60-day re-login cycle.

### Gaps
- The Reels scheduling window (29 days per secondary sources) and the exact primary wording of the specs were not read in full (developers.facebook.com blocked).
- Which Instagram figure, 100 or 50, Meta currently enforces: its own docs conflict. Check `content_publishing_limit` live.
- Whether Reels posted via `/{page-id}/videos` receive Reels distribution: not documented in sources found.

## Q4. Postiz: public API rate limits and how it handles TikTok, YouTube and Facebook Reels

### Takeaway
Reading the source code resolves the 90 versus 30 conflict. The NestJS throttler defaults to **90 requests per hour per organisation**, overridable by `API_LIMIT`, and the shipped `.env.example` sets **`API_LIMIT=30`**. The throttle counts only `POST /public/v1/posts` (and public comment POSTs); other endpoints are not throttled. Postiz refreshes and rotates TikTok tokens (assuming 23 h). It uses YouTube resumable upload and handles the new upload-bucket error. It does **not** use `/video_reels` for Facebook.

### Cited Findings
- `apps/backend/src/app.module.ts`: `ThrottlerModule.forRoot({ throttlers: [{ ttl: 3600000, limit: process.env.API_LIMIT ? Number(process.env.API_LIMIT) : 90 }], storage: ThrottlerStorageRedisService })` — [app.module.ts [P-fetched]](https://raw.githubusercontent.com/gitroomhq/postiz-app/main/apps/backend/src/app.module.ts)
- `throttler.provider.ts`: the guard only applies when `method === 'POST' && url.includes('/public/v1/posts')` or for public comment POSTs, and otherwise returns `true`. The tracker key is `org.id + '_posts'`, so the limit is per organisation, not per API key — [throttler.provider.ts [P-fetched]](https://raw.githubusercontent.com/gitroomhq/postiz-app/main/libraries/nestjs-libraries/src/throttler/throttler.provider.ts)
- `.env.example`: `API_LIMIT=30 # The limit of the public API hour limit` — [.env.example [P-fetched]](https://raw.githubusercontent.com/gitroomhq/postiz-app/main/.env.example)
- TikTok: `refreshToken()` POSTs `grant_type=refresh_token` to `https://open.tiktokapis.com/v2/oauth/token/` and returns the **new** `refresh_token`, with `expiresIn` hardcoded to 23 hours. It calls `creator_info/query` for `max_video_post_duration_sec`. Default `privacy_level` is `'PUBLIC_TO_EVERYONE'` when none is set; the TikTok guidelines require a manual choice with no default, so this is a potential audit problem for anyone copying it. `maxConcurrentJob = 10000`. Scopes include `video.publish` and `video.upload` — [tiktok.provider.ts [P-fetched]](https://raw.githubusercontent.com/gitroomhq/postiz-app/main/libraries/nestjs-libraries/src/integrations/social/tiktok.provider.ts)
- YouTube: resumable upload with 8 MB chunks and batches under 4 minutes. `privacyStatus: settings.type`. Handles `defaultVideoInsertPerDayPerProject`, `uploadLimitExceeded` and `rateLimitExceeded`. A thumbnail error says custom thumbnails need a phone-verified channel. `maxConcurrentJob = 200` — [youtube.provider.ts [P-fetched]](https://raw.githubusercontent.com/gitroomhq/postiz-app/main/libraries/nestjs-libraries/src/integrations/social/youtube.provider.ts)
- Facebook: `META_GRAPH_API_VERSION = 'v25.0'`. MP4 → `POST /{id}/videos` with `file_url`, `description` and `published: true`, then `finalUrl = 'https://www.facebook.com/reel/' + videoId`. Stories use `/video_stories`. The token is exchanged for a long-lived one (`fb_exchange_token`) and stored with a 59-day expiry. Scopes: `pages_show_list`, `pages_manage_posts`, `pages_manage_engagement`, `pages_read_engagement`, among others — [facebook.provider.ts [P-fetched]](https://raw.githubusercontent.com/gitroomhq/postiz-app/main/libraries/nestjs-libraries/src/integrations/social/facebook.provider.ts)
- The 100/h Postiz Cloud figure and the "90 self-hosted" docs wording come only from a docs snippet in the previous pass — [Postiz docs [S/snippet]](https://docs.postiz.com/public-api/introduction.md); the Mintlify "30 req/h global" page — [Mintlify [S]](https://www.mintlify.com/gitroomhq/postiz-app/api/rate-limits)

### Inferences
- Mintlify's "30/h global" is wrong on scope (only post creation is throttled), but right on the value for anyone who copies `.env.example`. Set `API_LIMIT` explicitly and batch several posts per call.
- Using Postiz as a publisher adds no TikTok, YouTube or Meta capacity. The self-hoster's own apps must still pass each platform's audit. Postiz's FB path (`/videos`) is not the documented Reels endpoint.

### Gaps
- Postiz's generic refresh scheduler (when it calls `refreshToken` relative to `expiresIn`) was only partly inspected: the interface has `refreshCron` and `refreshWait` flags. Whether a real 2 h TikTok access token causes failed posts before refresh was not tested.
- Postiz Cloud's actual limit (100/h) was not verified at a primary source.
